Ground rules kept while building: no paid plan or card required so far; test identities only (not a login); no public deployment before Phase 10 authentication; database changes and CI runs each need explicit approval first.
- Team codes expire 7 days after creation or regeneration (PRD B5 says codes can expire; the PRD sets no duration, so 7 days is a clearly labeled TEST default). Expiry is configurable by the owner per project in the Team sheet: no expiry, 1, 7 or 30 days, applied to the current code without changing it. Codes already issued keep their established conditions until the owner changes them. The owner sees the date in the Team sheet and regenerates to reopen joining. Teammates never receive the code or its state.
- Join limits (PRD B5 "limited in use") are owner-configurable per code: no limit (the default; no forced cap) or 1-1000 joins. Uses are counted on each successful join; an existing member retrying still gets the already-member message, and the limit refusal tells the joiner to ask the owner. Both controls are local reversible settings, no approval needed.

## Provider wiring (Ph 5-6; user approved "connect real AI" 10 Nov)

Own-key calls are real: adapters for the five named providers hit the official endpoints (docs.x.ai, docs.nvidia.com, aistudio.google.com, platform.claude.com, api.openai.com) straight from the device, key memory-only. O4 ("Grok" = xAI Grok or Groq) is not assumed: the picker asks which one. The owner model with a real owner key needs server-side key storage, which is auth-gated (O5), so teammates on the owner model stay simulated and are labeled as such. No live call is made in tests; the user's first real call is their own key use.

## Merge review and the main folder (PRD F6, acceptance 9; user approved 10 Nov)

Work in a task folder is a draft until the assignee submits it and the owner runs the integration check and merges it. A merge is refused while mismatches are open or when the folder changed after the last clean check (stale review).

Merge representation (approved as the listed "combine accepted work" item): accepting a merge copies every checked file `<folder>/<name>` to `main/<folder>/<name>`. Rationale: collision-free across folders, deterministic, preserves which task produced each file, and stays owner-only (teammates keep folder scope). The merged content is recorded per acceptance; a merged copy the owner edited since is never silently overwritten - the next merge is refused until the owner explicitly overwrites. Hosted/Drive-backed storage stays a separate decision (O9, auth-gated).

## Tool runtime boundary (Phase 8)

This is process isolation with filesystem restrictions, not a secure sandbox for hostile tools. Handlers never run in the app process: each run spawns the MCP server, a separate Node process under the runtime permission model (node --experimental-permission), which ENFORCES no filesystem reads outside the runner bundle, no filesystem writes, no child processes and no worker threads (a probe handler proves this in tests/toolproc.test.ts). Network is NOT runtime-enforced on this Node version: handlers are vetted in-repo code that receives only data strings, and a hostile-handler network guarantee would need an OS-level mechanism (e.g. a network namespace), which is not claimed and not built without infrastructure approval. Tool runs go through a genuine MCP server: src/mcp/server-entry.ts speaks the Model Context Protocol 2025-06-18 over stdio (newline-delimited JSON-RPC 2.0): initialize handshake with capability negotiation, tools/list with input schemas, tools/call with text content blocks, JSON-RPC error codes for unknown tools/methods. It is built in-repo with no external MCP packages and is not conformance-tested against the official SDK; protocol shape is grounded on the published spec. mcpclient.ts pipelines the lifecycle and matches replies by id.
